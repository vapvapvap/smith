# Эксперимент: стратегии управления контекстом агента Smith

- **Дата:** 2026-09-13
- **Ветка:** `L10`
- **Модель:** `deepseek-flash` (алиас `DEEPSEEK_FLASH`)
- **Бэкенд:** локальный `smith-backend`, `http://localhost:8080`
- **Режим:** реальные вызовы DeepSeek (`thinking=disabled`, `reasoning_effort=low`,
  `max_tokens=1500`), sync `POST /api/v1/chat/completions` + сервисные
  `POST /api/v1/chat/summarize` и `POST /api/v1/chat/facts`
- **Сценарий:** «собираем ТЗ» — 12 ходов пользователя, мобильное приложение
  доставки еды (см. `scenario.json`)

## 1. Цель

Сравнить 5 стратегий управления контекстом на одном сценарии по осям:

1. **качество ответа** — полнота и корректность итогового ТЗ;
2. **стабильность** — не теряются ли важные детали из начала диалога;
3. **расход токенов** — основной контекст + сервисные вызовы;
4. **удобство** — сколько ручных действий и прозрачность.

Стратегии:

| # | Стратегия | Идея |
|---|---|---|
| 1 | `as_is` («Как есть») | весь диалог передаётся без сжатия (дефолт) |
| 2 | `sliding_window` | только последние N сообщений |
| 3 | `sticky_facts` | блок `facts` (ключ-значение) + последние N сообщений; `facts` обновляются LLM после каждого хода |
| 4 | `branching` | checkpoint + 2 независимые ветки от одной точки |
| 5 | `summarize` | саммаризация каждые N сообщений (rolling) |

## 2. Методика

Скрипт `run_strategy.py` воспроизводит клиентскую логику сборки промпта
(`smith-frontend/js/app.js`, `buildPrompt`) и вызывает реальный backend.
Для каждого хода фиксируются `prompt`, ответ, `usage`; в конце — итоговое ТЗ.
Стабильность измеряется автоматически: доля ключевых деталей сценария
(платформы, бюджет, срок, оплата, 1С, 152-ФЗ и т.д.), найденных в итоговом ТЗ
(17 деталей, см. `scenario.json → key_details`).

Параметры окна: `window = 6`, `summary_interval = 6`.
Checkpoint для ветвления — после 6-го хода.

### Сценарий (12 ходов)

Цель → аудитория → платформы → функции → доставка/самовывоз → оплата/push →
бюджет/срок → 1С → дизайн → 152-ФЗ → монетизация → «собери итоговое ТЗ».

## 3. Результаты

### 3.1 Сводная таблица

| Стратегия | Основные токены | Сервисные токены | **Всего** | Контекст последнего запроса | Стабильность (детали) |
|---|---|---|---|---|---|
| `as_is` | 26 890 | 0 | **26 890** | 3 965 | **17 / 17** |
| `sliding_window` | 19 708 | 0 | **19 708** | 2 141 | 14 / 17 |
| `sticky_facts` | 18 428 | 13 663 | **32 091** | 1 707 | 7 / 17 |
| `summarize` | 15 128 | 10 390 | **25 518** | 1 829 | **17 / 17** |
| `branching` (A+B) | 25 458 + 11 877 | 0 (+ 7 764 префикс) | **45 099** | 4 034 (A) / 3 772 (B) | A 15/17 · B 12/17 |

> Для `branching`: общий префикс 6 ходов — 7 764 токена, затем независимо
> ветка A (продолжение сценария, 25 458) и ветка B (альтернатива, 11 877).
> Сопоставимый с `as_is` полный прогон (префикс + ветка A) = 33 222 токена.

### 3.2 Что потеряно (стабильность)

| Стратегия | Потерянные детали |
|---|---|
| `as_is` | — |
| `sliding_window` | Аудитория 18–45, Самовывоз, Русский язык |
| `sticky_facts` | iOS, Android, Бюджет 2,5 млн, Срок 4 мес., Аудитория, СБП, Оплата картой, Самовывоз, Геолокация, Push, Русский язык |
| `summarize` | — |
| `branching` A | Аудитория 18–45, Русский язык |
| `branching` B | Бюджет 2,5 млн, 1С, 152-ФЗ, Комиссия 15%, Дизайн (ветка B короче и сфокусирована на изменениях) |

### 3.3 Качество ответов (кратко)

- **`as_is`** — полное структурированное ТЗ: цель, аудитория, платформы, язык,
  функции, оплата, 1С, безопасность, монетизация, бюджет, срок. Все 17 деталей.
- **`summarize`** — полное ТЗ (17/17), сопоставимое с `as_is`, при меньшем
  контексте. Детали не потеряны, структура сохранена.
- **`sliding_window`** — ТЗ содержит детали из последних 6 ходов (бюджет, срок,
  монетизация, дизайн, 152-ФЗ), но теряет ранние (аудитория, самовывоз, язык) и
  добавляет предположения (Flutter, SMS-авторизация), которых в диалоге не было.
- **`sticky_facts`** — худший результат. Экстрактор фактов вместо извлечения
  требований начал «вести проект»: придумал блокер «блок 1 не закрыт»,
  гипотезу «собственная сеть ресторанов» (в диалоге её не было), условия
  закрытия. Эти домыслы стали фактами, вытеснили реальные требования
  (платформы, аудитория, оплата, доставка), и итоговый ответ отказался собирать
  ТЗ. Наблюдается **дрейф фактов** (fact drift) — накопление галлюцинаций и
  самореферентность.
- **`branching`** — ветки независимы: A воспроизводит основной сценарий
  (15/17, полное ТЗ), B корректно отражает альтернативу (Apple Pay, BNPL,
  3 млн, POS-интеграция). Ветвление работает как «параллельные диалоги».

## 4. Анализ по осям

### Качество
`summarize` ≈ `as_is` > `branching` A > `sliding_window` > `sticky_facts`.

### Стабильность
`as_is` = `summarize` (17/17) > `branching` A (15/17) > `sliding_window` (14/17)
> `sticky_facts` (7/17). Скользящее окно закономерно теряет ранние требования;
`sticky_facts` деградирует из-за дрейфа фактов.

### Расход токенов
`sliding_window` (19 708) < `summarize` (25 518) < `as_is` (26 890)
< `sticky_facts` (32 091) < `branching` (45 099 на две ветки).
При этом `sticky_facts` при самом дешёвом основном контексте (18 428) оказался
**дороже всех** из-за сервисных вызовов (13 663): обновление фактов на каждом
ходу удваивает расход. Контекст последнего запроса минимален у `sticky_facts`
(1 707) и `summarize` (1 829), максимален у `as_is` (3 965) — это важно для
лимита 1M токенов на длинных диалогах.

### Удобство
- `as_is` — ноль настроек, прозрачно.
- `sliding_window` / `summarize` — одно поле N.
- `sticky_facts` — автоматика, но факты нужно контролировать: при дрейфе
  пользователь может не заметить подмену требований (панель фактов помогает).
- `branching` — самые ручные действия: разветвить, переключаться между ветками.

## 5. Выводы

1. **Дефолт `as_is` оправдан** для коротких/средних диалогов: максимальная
   стабильность и качество при предсказуемом расходе.
2. **`summarize` — лучший баланс** для длинных диалогов: качество `as_is` при
   меньшем контексте последнего запроса и умеренной стоимости сервисных вызовов.
3. **`sliding_window`** применим, когда важны только последние реплики; на
   задачах со сквозными требованиями теряет детали и склонен додумывать.
4. **`sticky_facts` в текущей реализации не рекомендуется.** Инкрементальное
   LLM-обновление фактов без защиты от дрейфа приводит к галлюцинациям и потере
   требований. Требуется доработка: append-only-семантика (запрет удаления без
   основания), программная дедупликация, извлечение из всего диалога, реже —
   обновление, строгий структурированный формат вывода.
5. **`branching`** решает задачу сравнения альтернатив, а не экономии
   контекста: расход равен сумме веток (плюс общий префикс). Стабильность
   внутри ветки наследуется от выбранной стратегии сборки.

## 6. Ограничения эксперимента

- Один сценарий, одна модель (`deepseek-flash`), один прогон на стратегию
  (шум модели не усреднён).
- `key_details` — приблизительная метрика (поиск подстрок); часть деталей может
  быть перефразирована.
- Качество оценивалось качественно (чтение итоговых ТЗ).
- `sticky_facts` перепрогонялся после усиления промпта экстрактора: результат
  изменился с 6/17 на 7/17 — дрейф сохранился, что и зафиксировано.
- Ответы ограничены `max_tokens=1500`; для длинных ТЗ возможна обрезка
  (у `as_is`/`summarize` детали уложились).

## 7. Артефакты

| Файл | Что это |
|---|---|
| `scenario.json` | сценарий, ключевые детали, параметры окна |
| `run_strategy.py` | воспроизведение клиентской логики + прогон по стратегиям |
| `transcripts/as_is.json` | транскрипт (промпты, ответы, usage) |
| `transcripts/sliding_window.json` | то же |
| `transcripts/sticky_facts.json` | то же (+ факты по ходам) |
| `transcripts/summarize.json` | то же (+ саммари) |
| `transcripts/branching.json` | префикс + ветки A и B |
| `summary.json` | сводные метрики по стратегиям |
| `report.md` | этот отчёт |

Пароли и ключи в артефакты не включались (`SMITH_PASSWORD` — через переменную
окружения; cookie-сессия в `cookies.txt` — локальный артефакт, не коммитить).
